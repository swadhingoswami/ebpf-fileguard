# 05 — Policy Model

## Conceptual model

```
Rule  =  ( Resource ,  Process Identity ,  Operation ,  Decision )

Protected resource  =  resource listed by the administrator as sensitive
Default for protected  =  DENY
Default for everything else  =  normal Linux semantics (ALLOW)
```

Decision procedure (implemented identically by `DecisionEngine` in userspace
and by the eBPF program in kernel):

```
request (resource, process, operation)
    |
    +-- resource protected? ──NO──► ALLOW (unprotected)
    |
    YES
    |
    +-- explicit rule (resource, process, operation) matches?
    |        +-- YES ──► apply rule decision (ALLOW or DENY)
    |        +-- NO  ──► default decision (DENY for protected)
```

### Why default-deny for protected resources

- **Least privilege**: access exists only because an administrator said so.
- **Fail-safe**: new executables, unknown binaries and policy drift all end in
  denial, which is the observable, auditable outcome.
- **Simple to reason about**: one protected file + one allow rule is obviously
  correct; default-allow is obviously dangerous for secrets.

## On-disk format: JSON

```json
{
    "version": 1,
    "defaults": { "action": "DENY" },
    "protected_resources": [
        { "path": "/protected/secret.txt", "operation": "OPEN" }
    ],
    "rules": [
        {
            "id": "allow-backup-agent",
            "resource": "/protected/secret.txt",
            "operation": "OPEN",
            "process": { "type": "exe_path", "value": "/usr/local/bin/backup-agent" },
            "action": "ALLOW"
        }
    ]
}
```

### Why JSON

- Self-describing, easy to diff and review in code review tooling.
- First-class support in the C++ ecosystem; we use **nlohmann/json**
  (single-header, no external deps, no codegen).
- The policy is configuration **that will be generated by other tooling**
  (CI/CD, IaC), where JSON is ubiquitous.
- YAML would add a parser dependency and its many edge cases for zero
  MVP benefit; TOML is nice but less universal for nested rule lists.

### Validation (enforced by `Policy::validate` and `ConfigParser`)

- `version` non-negative.
- Every path absolute.
- `process.type` must be `exe_path` (other types are future levels).
- `operation` must be `OPEN` (MVP).
- `action` must be `ALLOW` or `DENY`.
- `rule.resource` must be listed in `protected_resources`.
- Rule ids unique; protected paths unique.
- At load time, `PolicyCompiler` additionally requires every path to **resolve
  via stat(2)** — a policy that references missing files is rejected, so a
  typo cannot silently install a policy that protects nothing.

## Process identity — levels and weaknesses

| Level | Identity | Weaknesses |
|---|---|---|
| 1 (MVP) | executable **path** (resolved to exe inode) | executable replacement changes identity (see Test 7); same binary used by many users is one identity; script shebang points at the interpreter, not the script |
| 2 | exe path **+ UID** | still path-based; setuid/setgid and process privilege changes are tricky |
| 3 | exe + UID + stable attrs (capabilities, mount ns, cgroup) | more inputs ⇒ more correct for containers; still not content-bound |
| 4 | **content hash** of the executable (measure at exec) | strongest against replacement; requires exec-time measurement and a trusted store (IMA-style); cost and complexity |

The MVP implements Level 1 **deliberately**, and the whole pipeline is built so
that higher levels slot in: `ProcessIdentity.type` already exists; the compiler
and map key simply grow.

### TOCTOU and executable replacement (Level-1 consequences)

- The policy is compiled from the **path** at install time. If
  `backup-agent` is later replaced by a different binary, the *old inode* no
  longer matches ⇒ the new binary is **denied** (fail-closed) until the policy
  is reloaded. That is the intended behavior and it is tested (Test 7).
- **TOCTOU on the resource**: the policy pins the *inode* of the protected
  file at install time. If an attacker swaps `/protected/secret.txt` for a
  different file, the *new* inode is not protected. Renames of the *original*
  file keep it protected (inode identity follows the file). Both behaviors are
  documented and tested (Tests 8-10). A hardened design would verify inode
  identity at open time against a whitelist keyed on path → inode and alert on
  drift.

## Policy update semantics

- **Atomic in userspace**: `shared_ptr<const Policy>` swap; readers always see
  an old or new complete policy.
- **Kernel**: two-phase update (disable → replace → enable) — never
  *inconsistent*, but has a bounded **fail-open window**. A truly atomic
  kernel swap would double-buffer the maps and flip a selector; that is the
  documented Phase-12 hardening step.
- **Rollback**: on any failure the old userspace policy remains current. A
  failed kernel install leaves enforcement disabled until a successful load —
  fail-open, documented.
